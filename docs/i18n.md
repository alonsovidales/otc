# Localization

Every Off The Cloud app shows its text in the user's language: English (the source and the
fallback), Spanish, French, German, Italian, Portuguese (European) and Dutch.

## Decisions

- **Address**: informal in Spanish (tú), German (du), Italian (tu), Portuguese (tu) and Dutch
  (je); formal in French (vous).
- **Where the choice lives**: on the user's OTC device, per user. Every app follows it; with no
  choice (*Automatic*) each app uses its own system language.
- **It overrides** iOS's and Android's per-app language for our own text. System-drawn UI
  (permission prompts, share sheets, file pickers) stays in the system language.
- **Translations** are made by Claude and checked automatically (placeholders, tags, glossary,
  never-translate terms, length) with back-translation for sensitive keys. Spanish is also
  reviewed by hand.
- **Typed confirmations**: the account page shows and accepts the word in its own language
  (`site.account.delete.word`, review required; typing `delete` is accepted too), and the body it
  sends is always `{"confirm": "delete"}`. Deleting a user in Settings asks for the username, which
  is data and never translated.
- **Stays English**: the privacy policy and terms (legal text needs a professional translator),
  the otc-sync command line (its tray is translated), log lines, image tags and place names
  (they are search keys), release summaries, alerts written before the localized device
  release, text from friends' devices (shown as a detail), the bridge's JSON `error` texts and
  websocket replies (clients word them by `code`), store listings and screenshots.
- **Pushes** use the user's stored language, else the language of the app that last registered
  for pushes. A critical-update push carries a translated sentence, without the English summary.
- **Website**: the language is in the path (`/es/`, `/es/account`); `/` and `/account` redirect
  by `Accept-Language`. No language cookie.
- **Order**: every app's interface, the stored choice, pushes, new alerts and the device's most
  common replies first; then emails, the account page and the setup wizard; then the landing
  page and the rest of the device's replies.

## Languages

`i18n/languages.json` is the only list. Each language has:

| code | tag | Apple | Android | name |
|---|---|---|---|---|
| en | en | en | (default) | English |
| es | es | es | es | Español |
| fr | fr | fr | fr | Français |
| de | de | de | de | Deutsch |
| it | it | it | it | Italiano |
| pt | pt-PT | pt-PT | pt | Português |
| nl | nl | nl | nl | Nederlands |

- `code` is what is stored, sent on the wire and used in file names.
- `tag` drives plural rules and number/date formatting everywhere (`pt` alone means Brazilian
  rules and formats: 0 is singular, different separators).
- `status` is `shipping` or `draft`. Generated platform files contain shipping languages only;
  `make i18n DRAFT=1` adds drafts and a pseudo-locale for local testing and must never be
  committed. The Language picker stays hidden while English is the only shipping language.
- Matching a system language: by base language through the platform's matcher
  (`es-MX` -> es, `pt-BR` -> pt, `nl-BE` -> nl, `[ca-ES, es-ES]` -> es), else English. The Go
  programs (`i18n.Match`) accept only a same-base match: raw x/text would map gl-ES and eu to es.
  On Android the list only resolves this way with `localeFilters` (below): library resources ship
  87 locales, Catalan among them, and without the filter `[ca-ES, es-ES]` shows English.
- Formatting in Automatic: plural rules always use the canonical tag; formatters use the
  system's full locale when its base language is the effective language, else the canonical tag.
  One accepted exception: Android picks plural forms from the configuration's locale itself, so a
  pt-BR phone in Automatic uses Brazilian rules (0 takes the `one` form); choosing Português
  explicitly gives pt-PT. Only zero differs, and setting pt-PT in Automatic would make the
  system's per-app screen stop saying "System default".

## The stored choice

On the device, per user (each user instance has its own `settings` row):

```proto
message ReqEnvelope { ...; string lang = 2; }                // the app's effective language code, every request
message Settings    { ...; optional string language = 7; }   // always set by new devices; "" = Automatic
message Status      { ...; optional string language = 17; }
message SetLanguage { string language = 1; optional string expected = 2; }  // ReqEnvelope req_set_language = 138; Ack
message UpdatePushRegistrations { ...; string language = 9; } // the resolved push language, for the bridge
```

A field that is **absent** means the device predates localization; `""` means Automatic.

Each app keeps a **local copy** (survives sign-out and Log Out on every platform) and a
**pending** flag, and resolves its effective language:

1. the device's field when present (`""` -> step 3);
2. absent or not fetched yet: the local copy;
3. the system language, matched;
4. English.

Changing it in an app: save the local copy with `pending` (its time, and `expected`: the device
value the app last saw when the change was made, left out when it never saw one), switch the app
at once, send `SetLanguage{language, expected}`. One SetLanguage at a time; a change made while
one is on its way goes next, against the value just sent. The device's answers:

- `Ack{ok:true}` (also when the value was already that): no longer pending.
- `Ack{ok:false, code:"changed"}`: the device's value moved since `expected` (another app). No
  longer pending; the app reads Settings again and adopts the device's value.
- `unknown_payload`: a device too old to keep it. The change stays local and pending, and nothing
  more is sent until the next connection, when the device may have been updated.
- Anything else (`invalid_language`, a plain error, a timeout): still pending, sent again at the
  next connection.

A change still pending at a connection is sent before that connection's first Status or
Settings value can be adopted. The web and the phones send it only once the device has accepted
a sign-in - never before, so a pick on a signed-out screen never dials - and at every sign-in it
accepts, also one on a socket that was already open (web `noteLanguageSignIn`; iOS and Android
`LanguageSettings.connected()`, called by `OTCConnection` before that session's first Status or
Settings). For 30 s after the change or its last send - also after the device's ok, because the
device answers each request on its own and a Status read just before the change can arrive
after the ok - a different Status/Settings value is ignored. macOS and otc-sync also discard a
status answer to a request sent before the last SetLanguage was sent or answered (a status
epoch). The 30 s run from each send, so a change made long before a sign-in whose first
SetLanguage failed isn't replaced by the next poll (the web resets `at`; the phones `pendingAt`;
macOS `languagePendingSince`; otc-sync keeps the send time in memory, `langSentAt`, since
`language_pending` is the compare key between its processes). Seeing its own value clears
`pending`. Otherwise, a device value that differs from the copy becomes the copy, so the copy is
always what the app shows.

Sign-out, Log Out, Disconnect, or a change of device or password keeps the copy and drops the
pending change and the device value last seen: a change made against one device's value never
reaches whoever signs in next. The exception is a change made for the next device: with no device
set up (a fresh install's connect form or tray, after Disconnect; the phones' Welcome screen and
Bluetooth setup, after Log Out); with a device set up but no value of it seen since that device
and password were set or the app started (macOS `deviceSeen` nil; otc-sync: the tray or command
line has no `device_language` from the running sync; iOS and Android `seen` nil, kept in memory
only and forgotten when the device turns the password down and at `OTCConnection.invalidate()`:
new credentials, Log Out) - it never signed in to them (a wrong password, which only Disconnect
fixes), hasn't yet since launch, the device predates localization, or no otc-sync sync is
running; again before signing in to the device set up since; picked in the Mac's setup wizard
and carried to the device it sets up; or still pending when a phone leaves a device from the
"isn't available" or "can't connect" card (it never reached that device;
`loggedOut(carryPending:)`). Nothing was seen to compare it with, so it stays pending through
changes of device or password until the next sign-in, which makes it that device's and sends it
without `expected` (no Status value is adopted over it before that sign-in): that device keeps
the choice (a new one has Automatic), whatever another app set there before. macOS marks it
`languageForNextDevice`, otc-sync `language_next_device`, iOS and Android `forNextDevice`.
Relaunching is not a change of device: the Mac's first settings at launch keep a pending change,
and so does a phone's relaunch. On the phones new credentials alone (Save Connection, Save &
Retry, leaving the bridge: only `invalidate()`) forget just the value seen: a change made while
signed in keeps its `expected` and goes to whichever device signs in next, where "changed"
adopts that device's value. Their Settings' Log Out drops such a change and keeps one for the
next device; a "changed" whose Settings read fails drops it too, and the next Status value is
adopted.

Other apps learn of a change through `Status.language` (already polled) and
`Settings.language`; the phones re-read both when they come to the foreground. Android applies a
change made elsewhere at the next start or return to the foreground, never in the middle of a
form.

`SetLanguage` is owner-only (`processAuthRequest`, `websocket/language.go`; before sign-in and
for friends it is `not_authenticated`). The device stores `""` or anything matching
`^[a-z]{2,3}$` (so older devices accept languages added later; anything else is
`invalid_language`) and renders codes it has no catalog for in English. It compares and writes
under one settings lock (`settings.langMu`; one otc process owns each database) rather than with
a conditional UPDATE, whose affected-rows count can't tell an unchanged value from a lost race.
A database error is a plain error reply, which apps keep pending. On a database without the
column the value is kept in memory until a restart, and the request still succeeds.

Every client sets `lang` in exactly one place, **after** the request's build closure runs (iOS and
macOS build closures replace whole envelopes): iOS/Android `WSClient.exchange`, macOS
`WSClient.envelope`, otc-sync `Client.Request`, web `ws.ts` before `fromPartial`. Each has a test
that a replacing build closure still sends `lang`. The device normalizes it once per request
(`requestLang` in `processMessage`) and passes it to the three `process*` handlers as a
parameter, never as connection state: requests on one connection run concurrently.

## Text the device writes

- **Replies** to owner requests are rendered in `env.lang`. Requests without `lang` (released
  apps, friends, the bridge), with `en`, or in a language this build carries no text for
  (`devtext.English`) get exactly today's English, byte for byte: no isolation marks, no grouped
  numbers. That stays the regression suite (`websocket/replies_test.go`). Packages return
  devtext errors (`devtext.New`, `Wrap`, or `WithEnglish` when a path or a number would change
  the English; a typed error implements `Localized(lang)`, like `LockedByParentError`), so
  `errors.Is` keeps working. The reply site puts `devtext.Text(lang, err)` into its own
  sentence as the detail, or uses the helpers in `websocket/replies.go`: `errText(lang, err)`
  for a reply that is only `err`, `sayOr(lang, english, msg)` for a message whose catalog
  rendering would change today's English (a `user` or number argument), `notAvailableHere` for
  a child instance's refusal. A raw Go, OS or database error the device can't translate is the
  whole reply in English; in another language it goes after `dev.err.action_failed` ("The
  device couldn't do that: {detail}") as the detail. `processMessage` works out `lang` before
  its panic recovery, so "internal error" follows it too. Pre-auth and friend replies use one
  fixed message each; the ones that still carry raw detail, because removing it would change
  today's English, are GetFriendshipStatus's "error retreiving friendship: …" and "Error: …"
  (`dev.err.error_detail`) on Auth, FriendshipInterDelete, DidSendFriendshipReq and
  FriendshipInterRequest (not changed yet). "Duplicated file" stays English inside the
  translated wrappers: released apps match it.
- **Codes before prose**: replies that apps act on carry an `error_code`. New:
  `duplicated_file` (LinkFile, FinishUpload, UploadFile), shipped before any app sends `lang`.
  Apps check `code == "duplicated_file" || (code == "" && message ends with "Duplicated file")`,
  and the same for `unknown_payload`. Never add `Ack.code` values to GetPubKey or Auth replies
  (the phones read any code there as the bridge's device status).
- **Alerts** are stored as keys next to the English `title`/`details`, which keep being written
  byte for byte. Package `alerttext` holds an alert's text: `Alert{Title, Detail, Key, Args,
  DetailKey, DetailArgs}`, built with `New(title, detail i18n.Msg)`, `WithRaw(title, raw)` (raw:
  an error's own words, the same in every language) or `English(title, detail)` (no keys: text
  no key can say, such as several missing disks). Its English is `EnglishOf(msg)`, the
  catalog's English without the isolation marks, so it is the old English. The writers in
  `dao/notifications.go` (`AddErrorNotification`, `UpsertErrorNotification`,
  `AddStorageNotification`, `AddUpdateNotification`) take an `Alert`:
  - `notifications.msg_key` and `msg_args` (`{"<arg>": raw value}`) are the row's title; a row
    `UpsertErrorNotification` updates replaces them with its new title.
  - `msg_lines` is the details, one entry per line: `{"at": "<UTC RFC3339>", "key", "args"}`
    (the title the line had) plus either `"detail"` (raw text) or `"detail_key"` and
    `"detail_args"` (a translatable detail: integrity, memory hints, Wi-Fi, bridge). Storage and
    update rows have no time lines: their details are one entry holding only the detail. Lines
    render through `dev.alert.line.detail` ("{clock} {title}: {detail}") and
    `dev.alert.line.plain`, which are not stored, so translators may change the punctuation.
    Capped at 500 lines and 60000 bytes (`alerttext.MaxLines`, `MaxLinesBytes`); the JSON is
    about twice the English, so a very long group shows fewer lines in other languages.
  - `update_version`: update alerts are de-duplicated by version, with the legacy English titles
    still matched (`updateTitles` in `websocket/machine_alerts.go` keeps today's titles even if
    the title is reworded).

  `ListNotifications` renders Error and Update rows in `env.lang` with
  `dao.LocalizeNotifications(lang, rows)` (`localizeAlerts` in `machine_alerts.go`): one more
  `select … where uuid in (…)` per 200 rows, and none for a request that renders as English. The
  fallback is whole (`alerttext.Render`): an unknown key, args that don't match its declared
  names and types, a line that doesn't parse, or no lines while details exist show the stored
  English title and details, never a mix. An English-only error that joins a keyed group sets
  its `msg_*` to NULL, so that row stays English for good. On MySQL 1054 every write falls back
  to the English-only SQL. Keys written to the database are marked `"stored": true` and can never
  be deleted or have their arguments changed (add a new key instead); every `dev.alert.*` key
  needs a row in `everyAlertKey()` (`alerttext/alerttext_test.go`), and alerts are never built
  from literals.
- **Text written before any request** stores codes too: the runners' status JSON files (update,
  bridge, tailscale, wifi restart) gain `code` and `args` next to `message`; the Wi-Fi change's
  `/run/otc-wifi-join/status.json` (release 140, Settings › Wi-Fi) has no `message` at all, only a
  `code`, the `ssid` and the `left`/`restored` flags, and the device words it from the key itself
  in every language, English included (`devtext.WifiJoinText`: `dev.status.wifi_join.<code>`, or
  `wifi_join_back.<code>` / `wifi_join_lost.<code>` for a failure after the device left its
  network, by whether it got back); wifiwatch's
  `pending_alert` is an `alerttext.Alert` (JSON `title`, `detail`, `key`, `args`, `detail_key`,
  `detail_args`; an older `{title, detail}` loads as English only), and its state keeps the speed
  before the restart as numbers (`slow_speed` `{rate, pct}`, next to the English `slow`; a
  failed restart's reason is the runner's `dev.status.wifi.*` key when its English equals the
  message); raidwatch keeps the port as data (and `capitalize` handles a multi-byte first
  letter) and hands its alert and push over as `Notify.AlertText` and `Notify.PushText` (one
  disk keyed, several English only); a shared-gallery job keeps its failure as a devtext error
  (`SharedGalleryJobState(id, lang)`). A runner's `code` is the last segment of its key,
  allowlisted per status file in package `devtext` (which also renders other packages' errors:
  `devtext.Text(lang, err)`), and `args` is an object of strings; `devtext/scripts_test.go`
  proves each script's `message` equals its key's English. `status.GetStatus(lang)` and
  `bridgeaccess.Status(lang)` render in the request's language.
- **Pushes**: rendered in the user's stored language, else `settings.last_ui_language`, else
  English (`push.ResolveLanguage`; `Push.Language`/`Push.Lang()` is the hook). `last_ui_language`
  is written only after an owner session's push registration (RegisterApnsToken,
  RegisterFcmToken, RegisterWebPush) succeeded, from `env.lang` when `i18n.Normalize` accepts it,
  and only when it changes. Apps register again at each connection and when the language they
  show changes (web: an existing subscription, at each sign-in). The resolved language goes to
  the bridge as `UpdatePushRegistrations.language`, sent again when SetLanguage changes it.
  Push keys may only use `{name}`, `{version}` and `{port}`
  and no tags (the push privacy rule in `push/push.go`: a friend's name and a generic phrase,
  since Apple and Google can read payloads). The language itself becomes visible to them.
  A push is a `push.Text` (key and args) sent with `NotifyText` and rendered at delivery in the
  resolved language; the bridge's offline alert is `push.OfflineAlert`.
- **Setup wizard** (`scripts/setup_wizard.py`, keys `wiz.*`): `?lang=` on the page, else
  `Accept-Language` (by q, base language only), else English. A language that came from the
  request is resent on every `/api` call (Bluetooth forwards the path, not headers) and kept by
  the hand-off to the LAN address; the English default sends nothing. The apps load the page
  with their effective language: iOS `otc-setup://device/?lang=<code>` (`BLESetupLang`),
  Android `https://device/?lang=<code>` (`BLESetupLang.pageUrl`, `LanguageSettings.wireCode`;
  `withLang` for the `/api` paths), the Mac
  `otc-setup://device/?lang=<code>` (`BLESetupTransport.lang`). Each appends `lang=` to every
  `/api…` path it forwards (the Mac's `withLanguage` also to `/`, keeping the page's query byte
  for byte) unless the path already has one; `/__otc/release` gets none. The phones use the
  language in effect at each call, the Mac the one the page loaded in. In a browser the page has
  a language list at the top right (a globe and a select, `wiz.page.language` its name): first
  Automatic, `wiz.page.language_auto` with the Accept-Language match by its own name (English
  when nothing matches), then each language by its own name (`LANGUAGES`, never translated).
  The page's data says which is chosen (`explicit`: the language came from `?lang=`) and what
  Automatic gives (`auto`). Picking a language reloads the page with `?lang=<code>` on the same
  step; Automatic reloads it without `?lang=`, dropping the choice; picking what the page already
  shows (the browser's language by name, or Automatic over that language) only rewrites the
  address. The reload keeps the state in `sessionStorage` (`otc-setup-keep`: this tab, read once,
  30 minutes): the step (2 to 4), the network and disks picked, the account step's mode and fields, the
  name (checked again) and the profile - never a password nor the terms checkbox. With passwords
  typed it asks first (`wiz.page.language_passwords`; `wiz.page.language_lost` when this browser
  can't keep anything), and it waits while the wizard isn't answering or a Wi-Fi join is under
  way. Inside the apps the list is hidden - the app's own choice is the one that counts - and
  the app calls `window.otcSetupLang(code)` instead, which takes the same path (true when the
  page goes to that language - at once, after that question, or once the wizard answers again;
  false when there is nothing to do).
  The Mac's setup window has a language menu (`LanguageMenu`: a globe and
  the language's own name, at the top right of each step and at the right of the Bluetooth step's
  bottom bar; Settings' list). A change before the page is up loads it in the new language; once
  it is up the page is asked to re-word itself (`window.otcSetupLang`), and a wizard without that
  call is reloaded once the device is installing, when it shows only the device's state (until
  then a line under it says so, `macos.bluetooth.language_later`). A language picked in the
  wizard goes to the device it sets up when "Sync this Mac with my device" signs in to it.
  The phones' Bluetooth setup has their `LanguageMenu` at the top right ("Each platform"), both
  while looking for a device and while the page shows; the screen's title wraps to two lines
  rather than being cut beside it (iOS a `.principal` title, Android a `BasicText` of at most two
  lines that shrinks to 70%). A change with no page up yet loads it in the new language; one
  while the page is still loading loads it again; once it has loaded the page is asked to
  re-word itself with `window.otcSetupLang&&window.otcSetupLang("<code>")` (the code
  JSON-quoted; iOS `evaluateJavaScript`, Android `evaluateJavascript` with `JSONObject.quote`),
  and a true or false answer means the page handles it. Anything else (an older wizard: nothing
  on iOS, "null" on Android) waits, unless the page is already in that language, until
  `/api/state` shows the install started (`install.phase` not `idle`, or `already_installed`)
  and the link is up, then reloads the page in it; until then a line over the page says so
  (`ios.setup_language_later`, `android.setup_language_later`, both with the translations of
  `macos.bluetooth.language_later`). iOS keeps this in `BLESetupTransport` (`waitingLang`,
  `installStarted`, `appLanguageChanged`, `reloadWhenSafe`), Android in `SetupPage` and
  `BLESetupLang` (`BluetoothSetupView.kt`). Android keeps the screen in place through the change
  (`LanguageSettings.holdInPlace()`), so the link and the page survive it. A language picked
  there goes to the device set up at the first sign-in to it, without `expected`.
  - Backend error answers carry `{"error": <today's English>, "code", "args"}` (`err_body`), and
    the bridge's refusals are passed on with the bridge's `error`, `code` and `args`
    (`bridge_error`). The page shows a translation only when the key's English with those args
    equals `error` (`known`; `errOf` tries `wiz.error.<code>`, then `wiz.bridge.<code>`),
    otherwise `error` itself: a bridge text reworded later shows in English until `wiz.bridge.*`
    follows.
  - install.sh writes `[otc-install] @step <token> [<json-args>]` and `[otc-install] @error
    <token> <json-args>` (`wiz_step`, `wiz_error`) before its English `[n/10]` and ERROR lines;
    old wizards ignore them. The wizard maps a mark to `wiz.install.step.<token>` or
    `wiz.install.error.<token>` and uses it only when that key's English equals the line that
    follows (`Install._marked`); marks never become the detail line or enter the page's log
    tail. The install state (also in `setup-final.json`) gains `text_code`/`text_args` and
    `error_code`/`error_args` next to the English `text`/`error`.
  - Sign-up sends `lang` to the bridge's `/api/account/signup` only when the language came from
    the request and isn't English: the apps pass `en` whenever they fall back to it, and the
    bridge keeps `""` for a language it can't tell, so a later bridge can still pick the
    person's language.
  - The page builds every node with `h()` and `rich()` (`innerHTML` only for the constant SVGs:
    the logos, the globe). The generated dictionary carries no argument types, so `t()`
    isolates arguments by name (`USER_ARGS = ['ssid','email']`): a new `user` argument in
    `wiz.*` uses one of those names or is added there. In another language country names come
    from `Intl.DisplayNames`.
  - setup_ble.py's own answers and verified-install.sh's lines stay English. Translated wizards
    reach users with a new image.

### Schema

- Device `db/db.sql` (also embedded for new per-user databases), `install.sh
  apply_schema_migrations`, and the idempotent `scripts/updates/118.sh` for the primary and every
  `^otc_[0-9a-f]{32}$` database: `settings.language VARCHAR(16) NOT NULL DEFAULT ''`,
  `settings.last_ui_language VARCHAR(16) NOT NULL DEFAULT ''`, `notifications.msg_key
  VARCHAR(96) NULL`, `msg_args MEDIUMTEXT NULL`, `msg_lines MEDIUMTEXT NULL`, `update_version
  VARCHAR(16) NULL`. A binary newer than its schema carries on with the defaults: MySQL 1054
  maps to `dao.ErrSchemaBehind`, the pattern for any column added later.
- Bridge migration `010-language.sql`: `accounts.lang VARCHAR(16) NOT NULL DEFAULT ''`,
  `push_registrations.language VARCHAR(16) NOT NULL DEFAULT ''`. Run by hand on bridge1, checked
  on bridge2, before the binary is deployed. The binary tolerates the columns being absent
  (`bridge/dao/language.go`): a 1054 naming the column marks it missing, the query runs again
  without it, and the column is tried again every 5 minutes, so the migration needs no restart.
  Only `PUT /api/account/language` refuses then (500 `save_unavailable`).

## Translations: one source

```
i18n/
  languages.json                    codes, tags, platform names, status, prefix routes
  glossary.md, glossary/<code>.json terms and tone per language
  strings/en/<prefix>.json          the source
  strings/<code>/<prefix>.json      translations
  catalog/<code>/<prefix>.json      generated, embedded by the Go programs
  cmd/i18ngen                       generator and checker (make i18n, make i18n-check)
```

**Keys** match `^[a-z][a-z0-9]*(\.[a-z0-9]+(_[a-z0-9]+)*)+$` and start with a prefix that says who
uses them:

| prefix | used by |
|---|---|
| `common` | every client (frozen early: buttons like Cancel, Delete) |
| `web` | web app |
| `app` | iOS and Android (always the same key in both) |
| `ios`, `android` | one phone app only |
| `desk` | macOS app and otc-sync (always the same key in both) |
| `macos` | macOS only |
| `dev` | device replies and alerts |
| `push` | device and bridge pushes |
| `mail`, `api`, `site` | bridge emails, API errors, public pages |
| `wiz` | setup wizard |

The checker fails on duplicate keys and on collisions after each platform's renaming (Android
`.` -> `_`, Swift/Kotlin camelCase, Swift keywords).

**English entry** (`i18n/strings/en/app.photos.json`):

```json
{"app.photos.deleted_by": {
  "text": {"one": "{name} deleted a photo", "other": "{name} deleted {count} photos"},
  "args": [["name", "user"], ["count", "count"]],
  "note": "Alert line in Notifications",
  "max": 60}}
```

Optional fields: `max` (length), `rich` (allowed tags), `stored` (written to the database),
`review: "required"` (consent, legal, security, destructive text; needs `"reviewed": "<who>
<date>"`), `translate: false`.

**Translation entry** (`i18n/strings/es/app.photos.json`): the text and the English it came from.

```json
{"app.photos.deleted_by": {
  "text": {"one": "{name} borró una foto", "other": "{name} borró {count} fotos"},
  "en": {"one": "{name} deleted a photo", "other": "{name} deleted {count} photos"}}}
```

A translation whose `en` differs from today's English is **stale**: development builds fall back to
English, Apple marks it `needs_review`, and the release check fails.

**Arguments** are declared in order; position N is the declared order in every language and
accessor. Types: `text`, `user` (user-controlled: wrapped in FSI/PDI isolation marks), `count`
(the integer that picks the plural form, at most one per key), `int`; for keys rendered by Go
from stored data also `bytes`, `datetime` (unix seconds) and `msg` (a sub-key from an allowlist).

**Plurals** are exactly `{"one", "other"}`. A special text for zero is its own key chosen in code.
`one` may leave out `{count}` only where one means exactly 1 (not French, where 0 is `one`).
Runtimes pick `forms[select(n)] ?? forms.other`. Android's generated files copy `other` into
`many` for es, fr, it and pt (lint requires it). A sentence that would need two plurals ("Delete
2 photos and 1 video?") takes its counted pieces as a `text` argument: each piece is its own
plural key, and the sentence gets them as `{what}` (`web.images.delete.title` with
`web.images.count.photos`, `count.videos` or `count.photos_and_videos`); its note says where the
argument comes from.

**Rich text** marks spans with tags: `Read the <link>privacy policy</link>`. Tags match
`<[a-z][a-z0-9]*>...</...>`, no attributes or entities; a translation's tags equal the English
ones; every URL comes from code.

### Rendering contract (security)

- A template is split into text, tag and placeholder tokens first; arguments are inserted as
  plain text in one pass and never scanned again (JS: a replacer function).
- Never render translated text or arguments as markup: no `innerHTML`/`dangerouslySetInnerHTML`
  with text, no `Html.fromHtml`/`HtmlCompat`/`AnnotatedString.fromHtml`, no
  `AttributedString(markdown:)`, no `Text(LocalizedStringKey(...))`.
- Rich keys have their own accessors (web `<Trans>`, Swift returning `AttributedString`, Kotlin
  returning `AnnotatedString`); a plain lookup of a rich key is a type error.
- Generators that write HTML, JS or Python treat translations as data: never template source,
  never `template.HTML`. Inline dictionaries go in `<script type="application/json">` written by
  encoding/json (HTML-escaped) and read with `JSON.parse`; the wizard's is one JSON literal
  checked by parsing `setup_wizard.py` with Python's `ast`.
- The checker rejects attributes, unknown or unbalanced tags, `<script`, `on…=`, `javascript:`,
  URLs, emails or domains not in the English verbatim, control and bidi-override characters,
  leading/trailing or double spaces, and tags in keys Go renders (except `site.*`, rendered
  through html/template). A hostile-catalog test runs `</script><img onerror>`, `"""`, `{{.}}`,
  `%s%n` and `$&` through every emitter.
- Zenity list text, and a list's `--text` on Linux (`listText`), goes through `xml.EscapeText`
  (zenity renders Pango markup in lists; message dialogs open with `--no-markup`); zenity
  selections map back by index.
- The bridge's site pages get a CSP with a nonce per response (`cSitePolicy` in
  `bridge/api/site.go`); their JSON text blocks are data and never run.

### Never translated

Off The Cloud, Tailscale, GitHub, Google, Apple; `Ack.code`/`error_code` values; protocol values
(the confirmation word sent to the server, otc-sync's `yes`); push data keys; notification types;
runner tokens; install.sh's own lines (the wizard words its steps from the marks); the SSID and
`OTC <id>`; stored defaults sent to friends; command-line words; file names the apps write
(conflict copies, `.otc-part`, renames, zips); contact-form reason values. What a server
receives for a typed confirmation is a code constant; the word typed is either data (a username)
or a translated key compared on the page, with the constant accepted too (the account page's
`site.account.delete.word`, "Decisions").

Logs stay English constants: the i18n layer never logs arguments (a missing key logs the key at
Error, arguments at Debug at most), `msg_args` never reaches a log, and the bridge never logs
rendered text or a language next to a domain or account.

### Generated files

`make i18n` (`go run ./i18n/cmd/i18ngen`) writes, per prefix, for shipping languages only, every
key in every language (English where untranslated). The exception is the Go catalog and the
wizard's dictionary: their non-English files hold only real translations, and the runtime falls
back to English key by key, with English plural rules (an English copy in the French file would
read "Syncing 0 file"). All are committed (devices build from `git archive`; the Go runtime's
embed fails to compile without `i18n/catalog`).

Placeholders per platform: web and Go substitute `{name}` at runtime (the web files rename them
to the TypeScript argument, `{file_name}` -> `{fileName}`, carry a plural's count argument as
`arg`, and already hold the isolation marks around `user` arguments, as Android's resources do);
Apple uses `%N$@`, `%N$lld`
for `int`, and the substitutions form `%#@count@` (argNum, `lld`, `%arg`) for plurals; Android uses
`%N$s` with numbers preformatted by ICU (`count` also passed as the quantity). A literal `%` is
`%%` on Apple, and on Android when the key has arguments (`formatted="false"` otherwise). Android
escapes `\ ' "`, newlines and tabs, `&` and `<`, and a leading `@` or `?`.

`make i18n-check` runs the generator in check mode, the validators, the hard-coded-text scanners
(`i18n/scan/README.md`; a ratchet against `i18n/scan/baseline/<surface>.json`: fails only when a
count rises) and vets and builds what embeds the catalog (the i18n packages, otc-sync for Linux
and Windows too, the bridge). It never writes a file. It runs from `scripts/release.sh` (on a
`git archive` of HEAD), `scripts/desktop-release.sh`, `bridge/makefile`, `make android-release`
and `.github/workflows/i18n.yml`; the release paths pass `I18N_RELEASE=1`, which turns stale,
missing or unreviewed text in a shipping language into an error. App Store uploads have no script:
run `make i18n-check I18N_RELEASE=1` by hand before one. The web surface's scanner needs node and
`web/node_modules`; `I18N_SCAN_FLAGS="-surface ..."` narrows it on a machine without them.

## Each platform

Every app shows the device's and the bridge's own words (`error_message`, `Ack.error_msg`, a
status message) as they come: the device already wrote them in the request's `lang`. An app's
own key is only the fallback when they are empty, and its own sentence goes before them as a
separate key, never as concatenated pieces. Models keep keys, state or enums and make the text
when it is shown. Tests that compare English keep their expected strings.

Patterns every app follows:

- A date the code wrote by hand is a key with its pieces as `text` arguments: "{month} {year}"
  (`web.images.grid.month_title`, `app.photos.months.title`), "{day} {month} {year}" (a tile's
  date: `web.images.grid.date`, `app.photos.months.day`). The web takes month names from
  `Intl.DateTimeFormat(t.tag, {month})`; the phones take them from catalog keys
  (`app.photos.months.<month>` and `_short`), so English keeps the web's "Sep" and Android's month
  functions stay testable on the JVM.
- A list of names is two keys used recursively, "{first} and {second}" and "{first}, {rest}"
  (`web.images.people.names_two`/`names_more`, `app.photos.people.list_two`/`list_more`), not
  `Intl.ListFormat`, whose English adds an Oxford comma the old text didn't have.
- A default the person may edit (a shared gallery's "Shared Media {date}",
  `web.files.share.default_description`, `app.files.gallery_default_description`) is translated
  once, when it is made; after that it is the person's text.
- Relative times are keys: `web.social.time.*` on the web, `app.shell.time_*` on both phones
  (the Social feed; on Android also the alerts and Shared Links). English abbreviates ("5h
  ago"); another language may use its own "ago" wording ("il y a 5 h", "vor 5 Std."), at most
  24 characters. iOS's alerts use `RelativeDateTimeFormatter`: abbreviated in English, the short
  style in the others, whose abbreviated one reads "-5 h" in French.
- A number written by hand ("%.1f", "42%") follows the app's language through its canonical
  tag, never the region, so English stays byte for byte: the web's `plainNumber`, `percentText`
  and `unitText` (below); on iOS `decimalText` (`SharedGalleryShareFlow.swift`: sizes, Settings'
  CPU and usage figures) and the side menu's CPU and mirror-sync percentages
  (`StorageSummary.trim`, "3,5" in Spanish); on Android `decimalText` (`ui/common/Util.kt`, with
  `LanguageSettings.numberLocale`: Settings' sizes, the status line's CPU and users' usage
  figures, and `formatBytes`'s sizes in Files, versions, Shared Links and the shared-gallery
  sheet; its KB keep no decimal, iOS's one) and the side menu's percentages (`pctText`: no
  grouping, at most two decimals); on the Mac and in otc-sync `desk.main.percent` ("{percent}%",
  "{percent} %" in French, Spanish and German).

  the engine writes the English `error`/`current_file` to `state.json` as before, plus
  `msg_key`/`msg_args` for the tray to render; errors of ours carry a message (`Msg() i18n.Msg`:
  `wsclient.MsgError`, `config.InvalidError`, selfupdate's, the flasher's `msgError` in
  `flasher/text.go`), shown by the tray's dialogs and printed in English by the command line.
  The tray rewrites its fixed items at each refresh, so a language change shows without a
  restart; its dialogs (the device and password dialogs, "Set Up a New Device…") each take the
  menu's language as they open, and the device dialog saves over config.json as it is then, so a
  language picked while it is open stays. Windows' dialogs are narrow and cut what doesn't fit
  (241 pixels): there the device dialog asks with `desk.main.settings_hint_windows` ("Device name
  or address:", `max` 36) and the setup's SD card rows are the size, the disk's number and the
  name, shortened to 34 characters in all (`windowsCardRow`); Linux keeps
  `desk.main.settings_hint` and the cards' full labels. Windows' message boxes, dialogs and menus
  also draw the isolation marks around `user` arguments (and in the device's own words) as boxes:
  every text the tray hands zenity, systray or its Win32 picker goes through `nativeText`
  (`tray/native.go`), which leaves LRI/RLI/FSI/PDI out on Windows only - GTK isolates with them -
  and `TestNativeTextOnly` fails on a direct call. The elevated `otc-sync flash-device` takes `--lang`, passed only for a language other
  than English (English users' pkexec command line is unchanged), to word its errors'
  arguments (a disk's label, a size); its status file's error line gains `error_key` and
  `error_args` next to the English `error`, and the tray rebuilds the message with
  `i18n.ParseStored` (an unknown key or args that don't fit show the English alone). Errors that
  cross a process follow that pattern (`errorProgress`, `Progress.failed`).
- **bridge**: the landing, comparison, account, disabled and unavailable pages are html/template
  files in `bridge/site/pages/*.html` rendered from `site.*` and embedded in the binary (package
  `bridge/site`: `Render(page, lang, Options{Base, Nonce, Now})`, template functions `t`,
  `rich`, `lines`, `texts`, `series`, `jstexts` and `jsform` bound to the page's language; every
  link target is in `site.go`'s `tags` table or the page's script, never in the catalog). The
  landing and comparison pages (`social.html`, `alternative.html`, `drive.html`) share
  `pages/common.html` (the `head`, `icons`, `header` and `footer` definitions; the head's Open
  Graph tags and JSON-LD come from `head.go`) and `pages/site.css` (the `site-style` template);
  the comparison pages add `pages/compare.css` (`compare-style`); the header's and footer's links to the landing
  page's sections start with `.Sections`, `""` on the landing page and its address elsewhere.
  `bridge/api/site.go` serves them from the binary, never from `/var/www`, where older deploys
  left copies (a stale `account.html` there is never served). On the bridge's own host:

  | path | answer |
  |---|---|
  | `/`, `/account`, `/private-social-network`, `/google-photos-alternative`, `/google-drive-alternative` | English; 302 to the same page under `/<code>/` (query kept; the browser keeps the emails' `#verify=`/`#reset=` fragments) when `Accept-Language` prefers another carried language; `Vary: Accept-Language` |
  | `/<code>/`, `/<code>/account`, `/<code>/<comparison page>` | the page in that language; `/en/...` is English without the redirect (the switcher's English links); the canonical of an English address is the one without `/en` |
  | `/<code>` | 301 to `/<code>/` |
  | `/xx`, `/xx/`, `/xx/account`, `/xx/<comparison page>` (two or three lowercase letters, not carried) | 404 |
  | `/<code>/anything` | 404 (only the landing, account and comparison pages are localized) |
  | `/landing`, `/landing.html` | 301 to `/` |
  | `/account.html` | 301 to `/account` (query kept) |
  | `/disabled(.html)`, `/unavailable(.html)` | that page by `Accept-Language` (a preview) |
  | `/robots.txt`, `/sitemap.xml`, `/llms.txt` | written by `bridge/site/crawl.go`: the sitemap lists the landing and comparison pages in every carried language with their hreflang alternates, plus privacy and terms; `llms.txt` is rendered from the English catalog (`llmsText`) |
  | anything else | `serveStatic`: a file of `bridge/static` (privacy, terms, admin, fonts, images), else 404 - never the old web app's `index.html` an earlier deploy left in `/var/www` |

  Other methods than GET and HEAD on these paths get 405. The pages and the three crawler files
  are gzipped for a client that takes it (`Vary: Accept-Encoding`). `www.<tld>` is a 301 to the
  same path on the bridge's own host, and every answer for a device's address carries
  `X-Robots-Tag: noindex` (`noindexDevices`). On a device's address
  `serveOwnPage` renders the disabled or unavailable page by `Accept-Language` (`Vary`, the
  same status and Retry-After as before; no hreflang, the path is the device's). The landing,
  comparison and account pages have `hreflang` alternates for every carried language (its tag) plus
  `x-default` (the English address), absolute, and every page `Content-Language`. The footer's
  language switcher (each language's own name, the current one `aria-current="page"`) is
  rendered only once a second language ships. The contact form words the endpoint's codes itself
  (`site.landing.contact.error.*`, the server's English). `TestEnglishUnchanged` compares the
  rendered English with goldens taken from the original static pages (`testdata/account.golden`
  from the old `bridge/static/account.html`): never regenerate them from the templates. Privacy,
  terms and the admin panel stay in `bridge/static`.

  The account page (`site.account.*`) has the same nonce CSP (as a static file it had none; its
  `style=` attributes became classes) and is the one page whose script writes text, which it gets
  as JSON data blocks: `#account-page` (the page's `lang`, `tag` and `home`), `#account-text` (what
  the script writes, by name) and `#error-text` (`{"api": {code: text}, "signin": {code:
  text}, "wait": {code: text}, "retry": [text…], "fields": {code: text}}`: the API's codes worded
  by `api.error.*`, or by `site.account.error.*` where the page words a code its own way, a Google
  or Apple sign-in's `?error=` by `site.account.signin_error.*`, a 429 with Retry-After as its
  code's first sentence (`site.account.wait.*`) and "Try again in N minutes." - `retry[N]`, a
  `series` 0-60 of the plural `site.account.wait.retry`, so the plural rules stay the catalog's -
  and `profile_incomplete`'s per-field codes by `site.account.field_error.*`).
  `jstexts "name" key|(jsform "key" "arg" "type"…)…` builds
  them (`site.go`'s comment): a plain key gives a string and a rich key `[tag, text]` pairs, so the
  script never parses markup; placeholders stay `{name}` (a `user` argument's between FSI/PDI);
  `jsform` names a key's arguments with their types (`text`, `user`, `int`). The catalog renders
  the key with stand-ins that are swapped back to placeholders, so an English fallback works too;
  a key that doesn't render back with every placeholder, or whose arguments aren't exactly those,
  is a render error. The script's `t(name, values)` fills the placeholders in one pass and the
  page inserts text nodes only (`h()`, `rich()`; no `innerHTML`); an `int` is formatted in the
  page's language. An API answer shows the table's text for its `code`, else the server's English
  `error`, else the page's fallback; `?error=` is only looked up. English keeps the browser's own
  date format, plain numbers and the bridge's English country names; other languages use
  `Intl.DateTimeFormat`, `Intl.NumberFormat` and `Intl.DisplayNames` with the page's tag. The
  script navigates to `location.pathname`, so signing in or out stays in the page's language,
  and its home links go to `/` or `/<code>/`. Google and Apple sign-ins come back to `/account`,
  so their language comes from `Accept-Language`, not from the page the person started on. The
  page sets the emails' language (`accounts.lang`, below) in two ways: a sign-up from a
  non-English page sends `lang`, the page's code (the English page sends the old body, and the
  bridge keeps using `Accept-Language`); and when `/me` says `lang: ""` on a carried non-English
  page it sends one fire-and-forget `PUT /api/account/language` with the page's code, because
  accounts from before migration 010 have `""` and their emails would otherwise stay English for
  good. It never overwrites a language already set and never sends `en`, so `""` keeps meaning
  "not known". Its typed confirmation word is in "Decisions".

  The JSON `error` of every API answer stays English (`errorText` renders `"en"`; keys
  `api.error.<code>[_variant]`, only a fallback): the account page and the apps word an answer by
  its `code`.
  The Google and Apple sign-in's plain-text error pages follow the browser's `Accept-Language`
  (`pageError`, `api.page.*`). Websocket replies are English (`relayText`, `api.relay.*`): the
  bridge never reads `ReqEnvelope.lang`. Emails (`bridge/accounts/emails.go`, `mail.*`, plain
  text as before) are written in the account's `accounts.lang`, never the requester's (anyone
  can ask a reset for an address); `""` or a code this build doesn't carry is English. The
  first email uses the language chosen at sign-up even where the column is missing. Their links
  open the account page in the email's language (`accountPage`; `pageLink` moves the verify and
  reset links, keeping their `#verify=`/`#reset=`): `https://<tld>/<code>/account`
  (`site.AccountPath`) for a carried language other than English, and `https://<tld>/account`,
  as before, for English, `""` and any other code. Names and addresses are `text` arguments, not
  `user`, on purpose: the English stays byte for byte, and a plain-text reader may show
  isolation marks, which spam filters score. The inactivity email's date is `mail.date.long`
  with the month keys; its `{day}` is a `count` only so that French can write the first of the
  month as "1er janvier 2027" (form `one`), and English's two forms are the same, so its text is
  unchanged. The stored `dev.alert.memory.restarted_times_day` keeps its `int` day (a stored
  key's arguments never change), so French writes "1 oct." there. `accounts.lang` is set at
  sign-up from the body's `lang`, else the first carried language in `Accept-Language` (Google and Apple sign-ups:
  `Accept-Language`), and `""` when none matches, not English, so a later bridge can tell it was
  never known. Changed only by the signed-in owner with `PUT /api/account/language {"lang"}`
  (errors `invalid_body`, `invalid_language`, `save_unavailable`); `/me` and the sign-in and
  sign-up answers carry it. `push_registrations.language` is
  `i18n.Normalize(UpdatePushRegistrations.language)`, and the offline alert takes its language
  from it (`offlineAlertText`); neither is logged next to an account or domain. OIDC redirects
  send `?error=<code>` and the account page never shows the parameter itself. `accounts.lang`
  and the push language are in the account export (`account.language`,
  `domains[].push_language`) and the privacy notice.

## Adding text

New user-visible text goes into `i18n/strings/en/<prefix>.json` with a `note` and its `args`,
then every other language, then `make i18n`; use the generated accessor. On the device, a reply's
text is a devtext error and an alert an `alerttext.Alert` from a `"stored": true` key ("Text
the device writes"). `make i18n-check` must pass before a release.
